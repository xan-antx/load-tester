    Evaluation: how we know it works

    This page explains how we measure that Elevate Load Tester does its job, and reports the numbers from real runs. Every figure here comes from a run made while building the features (12 November 2026). None of them are estimates.

    The runs used the bundled mock target (code/scripts/mock_target.py), a small login API whose behaviour we control. Because we know exactly how it should behave, we can check whether the tool reports the right things.

    1. What a correct run looks like on the mock target

    The mock is built with known properties:

    • Correct handling. Valid credentials (demo / demo123) give 200. Missing, null, empty or wrong-type usernames and passwords, wrong credentials and a negative expiresInMins give 400.
    • Optional field. expiresInMins is optional: missing, null or 0 is accepted.
    • Three deliberate bugs: 1. expiresInMins as text: unhandled exception, 500; 2. expiresInMins above 1,000,000: unhandled exception, 500; 3. a username longer than 256 characters: accepted with 200, a validation bug.
    • Load limits. A global rate limit of 40 requests/s (beyond it, 429), and 8 workers that each spend 50–150 ms per request (about 80 requests/s). Beyond that, requests queue and latency climbs.

    A correct tool should therefore:

    • find exactly the three bugs and report nothing else as wrong;
    • report a 429 as rate limiting, not as a bug;
    • put the capacity limit near the point where the mock runs out of workers.

    With default expectations. The two optional-field cases are flagged as "accepted invalid input" too: 20 of 166 requests in a 15-user, 15-second run. That is the right call for a tool that cannot know which fields are optional, and the per-case "expects 2xx" toggle exists for exactly this.

    • 497 rate-limited (429), correctly kept separate.

    3. SLO thresholds

    Default SLO in the app: p95 ≤ 500 ms and server errors (5xx + no answer) ≤ 1%. Three more thresholds are optional: average response time, unexpected-answer rate and minimum throughput.

    Run p95 Server errors Unexpected answers Verdict
    Evaluation run above (SLO also had unexpected ≤ 5%) 150 ms ✓ 6.23% ✗ 3.26% ✓ FAIL
    Browser run, 15 users × 15 s, all cases 150 ms ✓ 9.04% ✗ — FAIL
    CI gate config (known bugs excluded), local 160 ms ✓ 0.0% ✓ 0.0% ✓ PASS

    The failures are correct: the mock really does crash on two inputs. The SLO turns that into a clear FAIL rather than a number the reader has to judge.

All four runs, in three environments, agree on 120 / 140 users. The step size (20 users) is the resolution: the true limit lies between 120 and 140 users.

    5. The CI performance gate

    .github/workflows/ci.yml runs on every push and pull request to main. It starts the mock target and the backend, and runs cli.py with code/loadtest.ci.yml: 10 users for 25 s, the three known bugs excluded, p95 ≤ 500 ms, server errors ≤ 1%, unexpected answers ≤ 1%.

    The tests were 160 before this round. The new ones cover:

    • target guardrails, redirect re-checks, ownership and CORS (test_target_guard.py);
    • expected outcomes and the mock's validation bug (test_expectations.py);
    • SLO verdicts (test_slo.py);
    • the capacity finder, on synthetic history data (test_capacity.py);
    • the CLI, with mocked HTTP (test_cli.py);
    • the robustness fixes (test_robustness.py): the server-side limit of one active run (429), failed Locust exits and missing statistics, runs interrupted by a restart, split-run status kept current, and the read-only HEAD → GET → OPTIONS probe.

    Limitations of this evaluation

    • One machine. The load generator and the target ran on the same laptop, so absolute latencies include its own load. The shape of the results (the bugs found, the plateau, the breaking point) is what is being checked.
    • The CI gate on GitHub's runners. It is verified by running the same steps in a Linux container. The first real GitHub Actions run will confirm it on the hosted runners.
    • Approximate split-run p95. It is a request-weighted average, not a true percentile (see the README).
